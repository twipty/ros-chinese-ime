## 0. 结论

**B 取代 A 作为实施依据，A 保留作为"风格与退路"的参考。**

一句话理由：**B 是实测、A 是推算**。B 对 `.dat` 全部 44,355 码点做了真实字体 cmap 交叉实测，
拿到 100% 覆盖（文津宋体三件套 / Jigmo 三件套两条路）；A 的核心方案（全量 Noto + Plangothic）
只做到"预计 ≥99%"，Plangothic 的字体文件当时并未下载验证。

但 A 有两段内容不能随之下线，B 里没有等价物（§2）。所以处置是：**以 B 为主干，把 A 的
两段吸收进计划**，A 文档本身入库保留、标为"被 B 取代（风格与退路的来源）"。

## 1. 逐项对账

| 维度 | A（全量字形） | B（最少字体） | 判定 |
|---|---|---|---|
| 主方案 | 全量 Noto Sans CJK SC + Plangothic P1/P2 | 文津宋体 v2.100 P0+P2+P3 | **B** |
| 对 `.dat` 44,355 字覆盖 | ≈99%（**推算**，Plangothic 未下载） | **100%（实测 44,355/44,355）** | **B** |
| 字体家族数 | 2 个家族（Noto 黑体 + Plangothic 黑体） | 1 个家族（文津宋体，物理 3 个 TTF） | **B**（工程更简单） |
| 物理文件数 | 3（Noto SC + Plangothic P1 + P2） | 3（P0 + P2 + P3） | 平 |
| 体积 | ≈11 MB 子集 + 31 MB | 57.1 MB | A |
| 字形风格 vs 现有 UI | **黑体，与 Noto Sans SC 一致** | **宋体**，与现有黑体不一致 | **A**（见 §2.1） |
| 简体字形标准 | Noto 是简体 | 文津"大陆 G 源"，明确简体 | **B** |
| 授权 | OFL 1.1（两份，需处理 RFN） | OFL 1.1（一份，RFN 不改名即可） | **B** |
| 备选线 | Jigmo（明朝体，CC0） | Jigmo（明朝体，CC0，实测 100%） | 平（B 的备选更实） |
| 落地改动 | IME 自绘双字体 + 探针改字体链 + 安装器 | 同左 + 按平面选分片（规则更简单） | **B** |
| 数据层边界 | §7 明确"字形覆盖 ≠ 可拼音输入" | §3.2 复述同一条 | 平（A 写得更细） |

**统计口径一处要纠正**：A 说"全量 Noto 只覆盖 61.7%"，B 说"所有单文件字体最多 61.7%"，
两者一致、互不矛盾——因为 Unicode 汉字超 10 万而 TrueType `glyphID` 是 16 位
（上限 65,535），**单文件物理上装不下**。这条是本计划的硬约束，不是选型偏好。

## 2. 只有 A 写了、必须吸收的两段

### 2.1 字形风格不一致（B 只对 Jigmo 提了，没对自己的推荐项提）

B 推荐文津宋体，理由是"大陆简体字形 + OFL + TTF"，但它对风格冲突只批评了 Jigmo
（"明朝体、观感不统一"），**没提文津宋体也是宋体**。这会带来一个它没写的后果：

- 文津 **P0 覆盖基本区**（20,924/20,924），如果用 P0 当主字体，**常用字全变宋体**，
  与当前 `NotoSansSC-subset.ttf` / `DroidSansFallback` 的黑体观感直接冲突；
- 如果只用 P0 补扩展 A、主字体仍用 Noto 子集，就变成"**常用字黑体 + 生僻字宋体**"，
  正是 A 第 4 节批评 Jigmo 的那个问题，只是从"中日风格差异"降级为"宋黑差异"。

A 的方案（Noto + Plangothic）恰好是黑体接黑体，风格连续。所以：

> **决策点 D-F1**：字体链入口用黑体还是宋体。
> 这不是技术问题，是产品观感问题，应由项目 owner 拍板。两个可执行的选项：
> ① 全宋体（文津三件套，实测 100%，风格一次到位，代价是常用字观感变化）；
> ② 黑体优先（现有 Noto 子集 + 文津 P0/P2/P3 兜底，实测可算 100%，代价是生僻字宋体）。
> ③ 若要黑体且统一，得先按 A 的方法把 **Plangothic 下载后实测**（A 未做），
>    成本 1–2 小时，能换来"全黑体 + 100%"这个第三条路。

**在 D-F1 定案前不写死字体清单**——否则等于替 owner 做了观感决策。

### 2.2 非 BMP 渲染的退路（A §6）

两份都把"ReactOS GDI 对代理对 / SIP / TIP 的支持"列为 P0 未知项，但只有 A 给了退路：
**若 GDI 画不出，就把非 BMP 字渲染成 IDS 或 `U+20BB7` 形式的码点标签**，至少不出现静默方框。

这条决定了 F0 探针的判据要写成三分支（可画 / 画成方框 / 画错），而不是二分支。
B 的 §4 只写了"不可用则 IDS/`U+XXXX` 标签兜底"，方向对，但没写判据，容易被做成
"能跑就算过"。

## 3. 两份都没写清、我补进计划的三点

### 3.1 与现有运行时字形过滤的关系（接入的第一个功能点）

M2 的 P1-2（`UiCanRender()` + `GetGlyphIndicesW` 过滤）现在会把**渲染不了的字从候选里剔除**。
字体全覆盖之后如果不放宽这条，用户仍然拿不到扩展区字——区别只是"候选被过滤掉"
而不是"画成方框"，**体感一样**（打 `shi` 看不到「师」的扩展区同音字）。

所以 F 里程碑的第一个功能改动不是画字，而是**把过滤改成"三态"**：
有字形 → 正常显示；无字形但可兜底 → 显示码点标签；探针不可用 → 整体放行（现状保留）。

### 3.2 字体注册的位置（M0 教训的直接约束）

两份都把 `AddFontResourceW` + 写 `HKLM\...\Fonts` 写在安装器里，方向正确，但没写"为什么不能别处"。
必须写明：**字体注册只允许发生在安装器（用户态、交互进程）**，不得进 `DllMain` / `ImeInquire`。
理由就是 `M0-REDLINE-REVIEW.md` §13 的结论——登录路径上不做可能失败的事。
`check_m1.py` §6 现在已经是调用白名单断言，把 `AddFontResourceW` 写进 `DllMain` 会直接判红。

### 3.3 体积与分发形态

57 MB 字体（A 的 31 MB 也一样）不该进主发行包。计划里固定为**独立可选字体包**，
主包仍是 `.ime` + `.dat`；安装器 `/status` 要能报告"字体包是否安装、装了哪几片"。

## 4. 纳入计划：新增里程碑 F

插入位置：**X（结构治理）之后、M3 之前**，因为 F0 是一次半天到一天的探针，而它的结论
（GDI 能不能画非 BMP）会影响 M3 UI 工作的做法；但字体本体可以并行到 M3/M4 期间做。

| 阶段 | 内容 | 判据 |
|---|---|---|
| **F0** | GDI 能力探针：在 VM 里用真实 `TextOutW` / `GetGlyphIndicesW` 画 U+4E00 / U+20000 / U+30000 各 5 字 | 三分支结论：可画 / 方框 / 错字；**不需要装 57 MB 字体就能做**（先用系统已有字体试，再决定是否必须装） |
| **D-F1** | 字体链入口：黑体 or 宋体（§2.1 三选项） | owner 拍板；若选 ③ 需先实测 Plangothic |
| **F1** | 字体链单一真相源 + `GlyphProbe` 多字体 + 修非 BMP fail-open（`ime_ui.cpp` 现在 `codepoint > 0xFFFF` 直接放行） | 探针与绘制共用同一份配置常量；单测覆盖代理对判定 |
| **F2** | 候选窗逐字符分段绘制 + 度量按段累加 | 候选行不重叠、不截断；扩展区 5 字截图 |
| **F3** | 安装器字体安装/上报/卸载（`AddFontResourceW` + `Fonts` 键 + `WM_FONTCHANGE`），独立字体包 | `/status` 三态；`/u` 对称清理；**不碰登录路径** |
| **F4** | 过滤三态化（§3.1）+ 覆盖率回归 | `tools/coverage_report.py` 不受影响（它是数据层）；新增"字体覆盖 44,355/44,355"断言 |

**F0 可以先单独做**，与字体选型解耦；不做的风险是：买了 57 MB 字体、改了自绘，
最后发现 GDI 画不出 SIP 平面，整套样式要重做。
