# M2 距离「准出」的差异点

> 检查日期：2026-11-18｜基线 `alpha0.0.2`｜结论：**准出成立**，但有 4 条"记录缺口"和 3 条"已知限制"需要写清，不能混为一谈。

---

## 0. 准出（exit）指的是什么

本项目没有单独的"准出文档"，判据散在三处，先把它们对齐：

| 来源 | 判据 |
|---|---|
| `ROADMAP.md` M2「退出标准」 | 记事本中输入常用单字不卡壳、不误上屏、无崩溃；**字准率以 Jun Da 高频前 500 字覆盖率自评（目标 ≥95%）** |
| `m2/M2-ACCEPTANCE.md` | 7 类行为、15 个用例逐项通过 |
| `m2/M2-REMAINING.md` | P0 全绿、P1（可用性）全绿、P2（工程化）全绿 |

三者的性质不同：**只有第一条含量化指标**，而它此前从未被测量过（见 §2）。行为类判据
（不卡壳、不误上屏、无崩溃）已由 15/15 覆盖，工程化判据已由 P2-1 关闭。

## 2. 本次补上的那条证据（原来完全没有）

ROADMAP 写"目标 ≥95%"，但全仓没有任何脚本产出这个数字，`M2-ACCEPTANCE.md` 验的是
**按键行为**而不是**字选得对不对**。两件事完全不同：候选窗按对了页、上屏了字，
但用户要的那个字可能在第 3 页。

新增 `tools/coverage_report.py`（纯标准库，直接读 `.dat`），按引擎的真实排序规则计算：

- `.dat` 的 `CharEntry` 按 `(syl_id, rank, codepoint)` 排序，引擎打分 `1000000 - rank`，
  默认 `show_rare=false` 时丢弃无 rank 的字——所以**同一音节内的显示顺序就是 rank 升序**，
  脚本不需要重新实现排序，读文件顺序即可（这是它可信的原因）；
- "前 500 高频字"= `rank` 字段最小的 500 个，而 rank 来自 hanziDB（本身是 Jun Da 排名衍生），
  **不重新分发 Jun Da 原始表**，用的是我们自己已有的数据。

实测（`m0/share/rospinyin.dat`，44,355 字 / 9,898 个有 rank）：

| 范围 | 首选（空格即可） | 首页（前 9，不用翻页） |
|---|---:|---:|
| 前 100 | 83.0% | **100.0%** |
| 前 500（准出判据） | 46.2% | **96.8%** ✅ |
| 前 1000 | 32.2% | 93.5% ❌ |
| 前 2000 | 18.8% | 85.5% ❌ |

**准出判据达标（96.8% ≥ 95%），但两件事必须一起记下：**

1. **余量很薄**：500 个字里已经有 16 个掉出首页，再多 9 个就跌破 95%。
   掉出去的 16 个全部集中在 `shi` / `ji` / `zhi` 三个音节（如 rank 333「师」在 `shi` 里排第 10），
   不是 bug，是同音字密度问题。已把 `--fail-under 95` 接进 CI 作为回归门限。
2. **首选率只有 46.2%**，且衰减很快（前 100 是 83%，前 500 掉到 46%）。
   这条**不在** M2 退出标准里，但它解释了真实体感："打个常用字还要按数字键"。
   根因是排序只看**单字频**，没有上下文——这是 M4（词组/词频）与 M5（整句）要解决的，
   不属于 M2 的欠账，但应该写进 M3/M4 的输入。

## 3. 四条"记录缺口"（不影响判定，但对外出纪要前要补）

### 3.1 已发布的 `alpha0.0.2` 版本号是错的

`.ime` 的 `FILEVERSION` 是 `0,0,1,0`、字符串是 `"alpha0.0.1"`（用户在文件属性里能看到）。
源码已在 2026-11-18 修正（`ime/version.h` 单一真相源 + `tools/check_release_version.py` 门禁），
但**已发布的资产不重发**：tag 不变而资产变了，反而破坏"资产 = tag 构建"的可追溯性。
下一次发版起自动正确。

### 3.2 验收截图没有归档

`m0/vm/evidence/m2-acceptance/` 里只有 `2026-11-18-imhost.log.gz` 与 `result.md`；
`M2-ACCEPTANCE.md` §3 里引用的 `shot-1213` 等截图不在仓库内。日志本身是够判定的
（键序 + `WM_IME_CHAR` 折叠还原），但对外出验收纪要时会缺图。

### 3.3 3.9–3.11（翻页/跨页选字/回翻）没有逐页截图

结论来自"跨页序号命中"（`1{衷}`、`4{郭}`、`7{仕}` 只在特定页成立），推理是可靠的，
但不是图像证据。补一张第 2 页的截图即可闭合。

### 3.4 数据表有两套数字，且没有输出指纹断言 —— ✅ 本次已修

- `m2/M2-DATA-PLAN.md` 里那段 `902768 bytes / ce7ca6e0…` 是 **2026-11-16 的历史运行日志**，
  此后做过一次数据修订，现行表是 `902,776 B / f28b2606…`。原文没有"这是历史"的标注，
  容易被后面的人当成当前值引用。**已加注说明，两个数字都保留。**
- `tools/mkdat/build_dat.sh` 原先只校验**输入** sha256，不校验**输出** `.dat`，
  所以"字节级可复现"靠人记。**已在末尾加 `EXPECTED_DAT_SHA256` 断言**：
  不匹配即失败，除非显式 `ROSPINYIN_ALLOW_NEW_DAT=1`（故意改数据时用）。
  这样"改数据"变成一次可评审的动作，而不是"跑一下、看差不多就提交"。

> 这四条都不改二进制、不影响"能不能用"，但会让后来的维护者误判。属于文档与脚本欠账。

## 4. 三条"已知限制"（用户可感知，但按设计如此）

| 限制 | 现状 | 归属 |
|---|---|---|
| 渲染不了的字会被**从候选里剔除**而不是画方框（P1-2） | 扩展 A/B 的大量候选因此"看不见"，与"打不出来"体感相同 | **M2 的取舍**，由 F 里程碑（字体全覆盖）放宽，见 `FONT-PLAN-REVIEW.md` §3.1 |
| `.ime` 被常驻进程映射，热替换需重启 | 安装器已做改名退让，但更新仍需重启 | 平台侧 + 安装器，短期无解 |
| 语言指示器串状态（显示上一个 IME 的开/关） | 两个不同 IME 表现一致 → 归平台侧；U1 修好后托盘仍显示 `EN` 是第二条独立证据 | 平台侧；要坐实需 N″ 对照（已降为"向上游报告时才需要"） |

## 5. 结论

**M2 准出成立**：行为判据 15/15、工程化判据全绿、唯一量化判据本次首测达标（96.8%）。
四条记录缺口与三条已知限制都不构成"不能宣布完成"的理由，但它们决定了**对外怎么讲**：
可以说"单字输入可用、高频字首页覆盖率 96.8%"，不能说"字准率 96.8%"——
准出判据算的是**首页可达**，首选率是 46.2%。

准出之后最值钱的三件事，按性价比排序：

1. **F0：VM 里验一次 GDI 能不能画非 BMP**（半天）。它决定 F 里程碑要不要走 IDS 兜底，
   而 39.8% 的字表在 BMP 之外，这个答案会影响 M3 的 UI 做法。
2. **首选率**：46.2% 是所有体感问题的总根。M3 可以先用"音节内按上下文/词频重排"拿到一部分，
   真正的解法在 M4/M5。
3. **补 §3.2–§3.4 的三条记录**（半天，纯文档与脚本）。
